5. Settings route/structure
/dashboard/settings, with Profile, Email, Password / Security, Sessions and Preferences sections. Linked from the dashboard and authenticated account menu, including its existing mobile presentation. Authentication required, but unverified users may access their own account security/settings. Step23's verified-email requirements for critical business actions remain intact. Sign-in return paths explicitly allow settings, and the reauthenticate=1 flag lets an already-signed-in user renew session freshness only when returning to settings.

6. Profile-update behavior
Display name only, trimmed, 2–80 characters, safely rendered by React. Better Auth 1.7.7 updateUser updates the session-derived account and forwards its native cookies. Unknown/forged identity or security fields are rejected. Repeated profile saves use normal last-write-wins behavior. Avatar URL editing/storage is deferred: the existing app uses initials and has no established safe image storage/rendering system.

7. Email verification state
Current private email and server-read Verified / Not verified state. Unverified users get the existing Step23 resend form and persistent cooldown/abuse protections. No email-address change. Public recovery still uses generic enumeration-safe responses. No real external email was sent.

8. Password-change behavior
Better Auth 1.7.7 changePassword with currentPassword, newPassword and revokeOtherSessions=true. Current password required; existing 12–128 character policy and exact password whitespace preserved; confirmation must match. Wrong current password gets a safe message. Application code never writes Account.password or performs its own password hashing.
Installed behavior: Better Auth deletes ALL old persisted sessions, including the old current session, and creates a new session/cookie for this browser. The account endpoint forwards only native HttpOnly cookies, discarding the native JSON token/user payload. Runtime tests verified old cookies fail, replacement cookie works, old password fails and new password succeeds. No automatic email verification occurs.
Credential/session mutations use a per-account PostgreSQL advisory lock and re-read authentication after acquiring it, so duplicate credential submissions cannot use stale authorization. A separate pool of at most two short-lived lock connections avoids exhausting the existing five-connection application pool; maximum per-process database pool capacity is seven. Better Auth remains owner of all security mutations.

9. Session management
Supported listSessions, revokeSession and revokeOtherSessions APIs. Settings DTO includes only session ID, current marker, created/updated/expiry timestamps and coarse browser/OS summary. No IP, raw user agent, bearer token, access token or refresh token appears in settings props/JSON. A client session ID is resolved server-side within the current user's active sessions before its token is passed internally to Better Auth. Foreign/missing/already-revoked IDs receive the same safe idempotent result; current-session revocation is rejected with a Sign out instruction. Checkboxes confirm one-session/all-other-session revocation. Native listSessions freshness is preserved (default 24 hours); stale session lists prompt supported sign-in renewal.

10. Preferences
Optional IANA timezone, with available timezone suggestions and UTC. Blank clears it to null; unknown names and raw offsets are rejected. Stored for future display preferences only. Existing event timezone ownership, scheduling, reminders and motion preferences remain unchanged.

11. Authorization/privacy
Every mutation derives its owner from authoritative Better Auth session data. Strict request schemas, bounded 16KB bodies, exact environment APP_URL origin and cross-site Fetch Metadata rejection. Native origin/CSRF protections remain enabled; settings responses are no-store/no-referrer. Safe errors, no provider/Prisma diagnostics, no credential logging. Public event creator projection still selects only name, and existing public organization projections expose no account email/security data. Name is public wherever already used; email, timezone and session/account data are private. Existing auth get-session behavior is not replaced by a parallel system.

12. Rate limits
Persistent RateLimit atomic buckets, HMAC identities using AUTH_SECRET. Password changes: 5 attempts/account/15 minutes and 10/IP/15 minutes, including success and failed current-password attempts. Session mutations: 30/account/15 minutes and 60/IP/15 minutes. No restrictive limiter on ordinary profile/preference saves. Step23 verification: 60-second email cooldown, 5/email/hour, 20/IP/hour. Passwords/tokens never appear in rate keys. IP resolution uses the existing Better Auth proxy configuration.

13. Existing-user compatibility

New unverified users can manage their own profile/security and resend verification but remain gated from protected business activity. No production user was re-verified or had credentials/business data modified for testing.
