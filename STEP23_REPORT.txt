5. Better Auth verification integration

6. Verification-email behavior
New signups receive a branded HTML and plain-text email titled "Verify your Nexora email", with a Verify email CTA, fallback URL, 24-hour expiry note and ignore/private-link security note. Signup displays Check your email and resend/sign-in options. Native signup can create a session; authentication alone does not grant new unverified accounts application access.

7. Resend-verification behavior
Public email-identified flow on /verify-email and signup confirmation. Email is normalized and validated. Cookie context is removed so an unrelated signed-in identity cannot affect the public response. The submitted email is passed to Better Auth's supported sendVerificationEmail endpoint. All existing, nonexistent, already verified, throttled and provider-failure cases have the same generic response. The UI applies a 60-second resend cooldown; PostgreSQL enforces the actual limits.

8. Password-reset architecture
/forgot-password calls supported requestPasswordReset. The email's native /api/auth/reset-password/:token callback validates the token and redirects to /reset-password. The new-password form validates confirmation and the existing password policy before supported resetPassword changes credentials. Success clears the token-bearing history entry and redirects to /sign-in?reset=success with confirmation copy. Account.password is never written by application code.

9. Reset-email behavior
"Reset your Nexora password" subject; branded HTML and plain text; one reset CTA, fallback URL, one-hour expiry note, private-link and ignore-if-not-requested copy. Both auth callbacks use src/services/email/authentication.ts -> src/lib/email/transport.ts. No Resend client is created in auth UI or callbacks.

10. Password policy
Unchanged: minimum 12, maximum 128 characters; no forced complexity. Exact password whitespace is preserved. Confirmation must match. Both browser schema and server boundary validate; Better Auth independently enforces length and owns hashing.

11. Expiration/reuse protection
Verification: signed JWT, 24 hours; repeat verification is intentionally idempotent, not strictly single-use. Already-verified users return safe success; expired/invalid signatures fail.
Reset: one hour, cryptographically generated Better Auth token; verification.storeIdentifier="hashed" stores a SHA-256 token identifier, not the raw token. Better Auth's transaction-backed consumeVerificationValue consumes once, including under concurrent reset attempts, and rejects expiration. Verification cleanup is disabled to avoid unrelated expired-row deletion during auth reads; expired rows cannot authenticate. Native reset-callback rate limiting is disabled ONLY for its token-bearing path and replaced with a PostgreSQL IP-only bucket, preventing raw tokens entering RateLimit keys.

12. Session behavior after reset
revokeSessionsOnPasswordReset=true. Runtime tests confirmed every persisted session for the disposable reset user was deleted. Cookie caching remains disabled. Old password fails; new password succeeds. Reset does not automatically mark an email verified, so new unverified accounts still need verification before application access.

13. Existing-user compatibility policy
Better Auth requireEmailVerification remains false, preserving supported password sign-in for existing users. Newly created users have an input:false server-controlled verificationRequired flag. requireUser redirects new unverified accounts to /verify-email?required=1; getAuthorizedUser rejects them at mutation boundaries. Organization/event creation, team/invitation actions, content, attendance, tickets, reminders, participation, follows and notifications use these guards. Existing users with verificationRequired=false retain their legitimate access. The existing Neon account was unverified and is still unverified and usable; it was not falsely marked verified. No mass credential or emailVerified migration occurred.

14. Rate-limit protections
Persistent PostgreSQL RateLimit, atomic ON CONFLICT updates. HMAC-SHA256 identities use AUTH_SECRET so raw emails are not stored in keys. Recovery/resend: per flow, 1 request/email/60 seconds, 5/email/hour, shared 20/IP/hour across email flows. Signup also uses these buckets plus existing Better Auth 3/IP/minute. Supported Better Auth password-reset POST limit: 5/IP/minute. Reset callback: 30/IP/minute, hashed IP key with no token. Better Auth resolves/normalizes IPs; no guessed proxy ranges or disabled tracking. Render's trusted forwarded-IP configuration must remain correct. A missing trustworthy IP shares a conservative unknown bucket.

15. Enumeration/privacy protections
"If an account exists for that email, we sent instructions." No user-not-found/provider diagnostics in public recovery responses. A uniform 10-second response floor covers the centralized transport's 8-second timeout under normal database latency; extreme infrastructure delays are not claimed to be mathematically constant-time. Provider failures throw internally rather than pretending delivery succeeded. Origin must match environment-specific APP_URL for POST, cross-site Fetch Metadata is rejected, and Better Auth origin/CSRF/callback protections stay enabled. The API allowlist exposes only existing auth plus verification/reset endpoints. No passwords, tokens, API keys or auth secrets are logged. Next development incoming-request and server-action-argument logging is disabled. Referrer policy is no-referrer on auth pages and auth link responses; auth requests are no-store. Templates reuse Step22 HTML escaping and have no tracking pixels.
